## pre-migration-linux.yml

### CRITICAL — Hard blockers that prevent conversion

| Check | Reference |
|-------|-----------|
| **BTRFS root / BTRFS mounts** — virt-v2v cannot convert a guest whose root or any mounted filesystem is btrfs because it cannot resize btrfs volumes during conversion. | [virt-v2v man page — Free space for conversion](https://www.libguestfs.org/virt-v2v.1.html) |
| **Valid Platform (VMware)** — Confirms the VM is running on VMware vSphere before attempting migration. | [virt-v2v-input-vmware — Importing a guest](https://libguestfs.org/virt-v2v-input-vmware.1.html) |
| **open-vm-tools package** — virt-v2v requires open-vm-tools to be installed so it can perform a clean handoff (remove VMware drivers, install virtio). | [virt-v2v man page — Converting a Linux guest](https://www.libguestfs.org/virt-v2v.1.html) |
| **open-vm-tools service running** — The vmtoolsd daemon must be active for virt-v2v to coordinate with VMware during the final conversion step. | [VMware KB: open-vm-tools overview](https://kb.vmware.com/s/article/2073803) |
| **GRUB configs use UUID** — Device paths (e.g. `/dev/sda`) in `grub.cfg` will be invalid after migration because virtio disks appear as `/dev/vda`. UUIDs are portable. | [virt-v2v man page — Boot configuration](https://www.libguestfs.org/virt-v2v.1.html) |
| **fstab uses UUIDs** — `/etc/fstab` entries referencing `/dev/sd*` will cause mount failures after disk device rename. | [Red Hat KCS: fstab entries after P2V or V2V migration](https://access.redhat.com/solutions/1339763) |
| **GRUB_CMDLINE_LINUX uses UUID** — A `root=/dev/sda*` in `/etc/default/grub` survives a `grub2-mkconfig` rebuild and will break boot after migration. | [virt-v2v man page — Boot configuration](https://www.libguestfs.org/virt-v2v.1.html) |
| **/proc/cmdline device paths** — Documents the running kernel's cmdline; a mismatch between the running cmdline and grub.cfg can indicate an out-of-sync bootloader. | [virt-v2v man page — Boot configuration](https://www.libguestfs.org/virt-v2v.1.html) |

| **LUKS encrypted volumes** — virt-v2v can read LUKS volumes only when a key is supplied via `--key`. Unconditional LUKS without a supplied key is a conversion blocker. | [virt-v2v man page — `--key` option](https://www.libguestfs.org/virt-v2v.1.html) |
| **Software RAID arrays** — mdadm RAID arrays may lose device-name consistency after migration (device enumeration order can change). virt-v2v does not actively manage RAID assembly. | [virt-v2v man page — Unsupported features](https://www.libguestfs.org/virt-v2v.1.html) |
| **Kernel version compatibility** — virt-v2v requires a kernel ≥ 3.10 to include the virtio driver set. Very old kernels lack `virtio_blk` or `virtio_net`. | [virt-v2v-support — Supported guests](https://www.libguestfs.org/virt-v2v-support.1.html) |
| **UEFI boot mode** — virt-v2v supports UEFI guests but requires OVMF to be installed on the conversion host and target. The target must support UEFI. | [virt-v2v-support — Guest firmware](https://www.libguestfs.org/virt-v2v-support.1.html) |
| **Secure Boot state** — virt-v2v rebuilds the initramfs and injects virtio drivers, which breaks Secure Boot signature chains. Secure Boot must be disabled before conversion. | [virt-v2v-support — Guest firmware / Secure Boot](https://www.libguestfs.org/virt-v2v-support.1.html); [Red Hat Bugzilla #1726558](https://bugzilla.redhat.com/show_bug.cgi?id=1726558) |
| **EFI System Partition** — UEFI guests must have `/boot/efi` mounted as `vfat`. A missing or non-vfat ESP prevents virt-v2v from updating the UEFI boot entry. | [virt-v2v-support — Guest firmware](https://www.libguestfs.org/virt-v2v-support.1.html) |
| **ZFS filesystems** — virt-v2v has no native ZFS support. A guest with a ZFS root or data pool cannot be converted. | [virt-v2v man page — Unsupported features](https://www.libguestfs.org/virt-v2v.1.html) |
| **VMware paravirtual drivers (pvscsi, vmmemctl, vmci)** — These modules confirm the VM is running on VMware. Their presence is expected pre-migration and should be absent post-migration. | [VMware KB: VMware paravirtual SCSI overview](https://kb.vmware.com/s/article/1010398) |
| **dracut virtio configuration (RHEL)** — dracut must be configured to include virtio modules; otherwise an initramfs rebuild (e.g. after a kernel update) will omit them and break boot. | [Red Hat KCS: dracut modules for virtio](https://access.redhat.com/solutions/1958); [virt-v2v man page](https://www.libguestfs.org/virt-v2v.1.html) |

### HIGH — Issues that cause post-migration failures

| Check | Reference |
|-------|-----------|
| **ubuntu-minimal package** — Absence of `ubuntu-minimal` indicates a stripped Ubuntu install that may lack components virt-v2v depends on during customization. | [virt-v2v-support — Supported guests](https://www.libguestfs.org/virt-v2v-support.1.html) |
| **NFS/CIFS mounts in fstab** — NFS/CIFS mount points reference network paths that may not be reachable from the KVM host or the migrated VM's new network location. | [Red Hat MTV docs — Prerequisites](https://docs.redhat.com/en/documentation/migration_toolkit_for_virtualization/2.11/html/migrating_your_virtual_machines_to_red_hat_openshift_virtualization/) |
| **Multipath configuration** — Multipath devices use WWID-based naming tied to the storage topology. Post-migration the underlying paths change and multipath may fail to assemble correctly. | [Red Hat KCS: Multipath and V2V migration](https://access.redhat.com/solutions/3194332) |
| **SELinux mode** — Informational: reports current SELinux mode. virt-v2v handles SELinux relabeling automatically during conversion using `setfiles`. | [virt-v2v man page — `--no-selinux-relabel`](https://www.libguestfs.org/virt-v2v.1.html) |
| **SELinux autorelabel notification** — virt-v2v performs SELinux relabeling immediately during conversion. If relabeling fails (e.g. due to memory), it falls back to creating `/.autorelabel` for first-boot relabeling. | [virt-v2v man page — `--no-selinux-relabel`](https://www.libguestfs.org/virt-v2v.1.html) |
| **GRUB password protection** — A GRUB password hash tied to a specific passphrase must be preserved manually; virt-v2v does not migrate GRUB passwords. | [GNU GRUB manual — Security](https://www.gnu.org/software/grub/manual/grub/grub.html#Security) |
| **VMware legacy tools daemon** — `/usr/bin/vmware-toolsd` from proprietary VMware Tools conflicts with `open-vm-tools`. Both cannot coexist; the proprietary daemon must be removed before migration. | [VMware KB: Uninstalling VMware Tools](https://kb.vmware.com/s/article/1014522) |
| **Root filesystem free space** — virt-v2v requires at least 100 MB free on each filesystem it modifies, and checks for available inodes. The playbook uses a conservative 1 GB threshold. | [virt-v2v man page — Free space for conversion](https://www.libguestfs.org/virt-v2v.1.html) |
| **Total provisioned disk size** — Conversion time and target storage requirements are proportional to total provisioned disk size, not used space. | [virt-v2v man page — Free space in the host](https://www.libguestfs.org/virt-v2v.1.html) |
| **OverlayFS mounts** — OverlayFS (used by container runtimes and `systemd-volatile-root`) cannot be block-copied correctly by virt-v2v. | [virt-v2v man page — Unsupported features](https://www.libguestfs.org/virt-v2v.1.html) |
| **FIPS mode** — FIPS enforces integrity of the initramfs via kernel checksums. virt-v2v rebuilds the initramfs during conversion, which can break the FIPS integrity chain. | [Red Hat KCS: FIPS and V2V migration](https://access.redhat.com/solutions/7027814) |
| **NSX / vShield agent** — VMware NSX guest introspection and vShield Endpoint agents are hypervisor-coupled and will break network traffic or fail silently on KVM. | [VMware NSX documentation](https://docs.vmware.com/en/VMware-NSX/index.html) |
| **VMware Horizon / VDI agent** — Horizon View agents are VMware-specific and non-functional outside the VMware stack. | [VMware Horizon documentation](https://docs.vmware.com/en/VMware-Horizon/index.html) |
| **Running database services** — Databases must be quiesced (consistent snapshot state) before disk-level conversion to avoid data corruption. | [Red Hat MTV docs — Migration prerequisites](https://docs.redhat.com/en/documentation/migration_toolkit_for_virtualization/2.11/html/migrating_your_virtual_machines_to_red_hat_openshift_virtualization/) |
| **qemu-guest-agent availability in repos** — OpenShift Virtualization uses qemu-guest-agent for IP reporting, snapshot quiesce, and live migration. It must be installable from the guest's configured repos. | [MTV docs — Understanding MTV migration](https://docs.redhat.com/en/documentation/migration_toolkit_for_virtualization/2.11/html/migrating_your_virtual_machines_to_red_hat_openshift_virtualization/assembly_understanding-mtv-migration_mtv) |
| **EDR / AV agent detection** — EDR agents with tamper protection use `fanotify` hooks that can intercept virt-v2v's driver injection phase and block qemu-guest-agent installation post-migration. | [CrowdStrike KB: Allow-listing processes](https://supportportal.crowdstrike.com); [SentinelOne exclusion documentation](https://docs.sentinelone.com) |
| **Immutable files** — Files with the `immutable` attribute (`chattr +i`) cannot be modified by virt-v2v or post-migration cleanup scripts. | [Linux `chattr` man page](https://linux.die.net/man/1/chattr) |

### MEDIUM — Issues that cause degraded or unpredictable behavior

| Check | Reference |
|-------|-----------|
| **Bonding / bridge configurations** — Network bonding and bridge configs reference specific MAC addresses and interface names that change after migration. | [Red Hat KCS: Network bonding after V2V](https://access.redhat.com/solutions/1520223) |
| **Custom udev rules** — Rules referencing hardware IDs, MAC addresses, or kernel driver names (`vmxnet`, `e1000`) break after migration because the underlying hardware changes. | [systemd udev documentation](https://www.freedesktop.org/software/systemd/man/udev_rules.html) |
| **Network config conflicts** — Running both NetworkManager and legacy `ifcfg` scripts simultaneously causes unpredictable network state that survives migration. | [Red Hat KCS: NetworkManager and ifcfg coexistence](https://access.redhat.com/solutions/1415173) |
| **NTP / chrony configuration** — Large clock drift between source and target breaks TLS certificate validation and Kerberos authentication. | [Red Hat KCS: Clock sync after migration](https://access.redhat.com/solutions/17248) |
| **Non-virtio network drivers** — virt-v2v converts `e1000`, `vmxnet`, and similar drivers to `virtio_net`. Pre-migration detection confirms the driver is recognized and will be converted. | [virt-v2v man page — Converting a Linux guest](https://www.libguestfs.org/virt-v2v.1.html) |
| **LVM thin provisioning** — LVM thin pools present a logical capacity that may exceed physical capacity; virt-v2v copies provisioned blocks and may fail or produce an oversized image. | [virt-v2v man page — Unsupported features](https://www.libguestfs.org/virt-v2v.1.html) |
| **Legacy network interface naming** — `ethX` naming is non-deterministic; after migration the interface may be renamed by udev/systemd, breaking network configuration that references `eth0`. | [systemd predictable network interface names](https://systemd.io/PREDICTABLE_INTERFACE_NAMES/) |
| **Stale mtab entries** — `/etc/mtab` entries referencing `/dev/sd*` or NFS paths from the old hypervisor can confuse mount reconciliation during first boot. | [Linux `mtab` documentation](https://linux.die.net/man/5/fstab) |
| **cloud-init datasource configuration** — A datasource list locked to `NoCloud`, `ConfigDrive`, or `Ec2` will prevent cloud-init from reading the OpenShift Virtualization `VMwareGuestInfo` datasource on first boot. | [cloud-init datasource documentation](https://cloudinit.readthedocs.io/en/latest/reference/datasources.html) |
| **Hypervisor-specific kernel modules** — `vmxnet`, `vmhgfs`, `lpfc`, `qla2xxx` are VMware or FC HBA-specific modules that waste resources and may cause conflicts on KVM. | [virt-v2v man page — Converting a Linux guest](https://www.libguestfs.org/virt-v2v.1.html) |
| **Persistent net rules** — `/etc/udev/rules.d/70-persistent-net.rules` hardcodes MAC-to-interface mappings. Because the MAC changes after migration, the interface will not come up. Common on RHEL/CentOS 6. | [Red Hat KCS: 70-persistent-net.rules after V2V](https://access.redhat.com/solutions/49705) |
| **Hardware-dependent systemd units** — Units with `After=/dev/*` or `Requires=/dev/*` reference hardware paths that change after migration, causing units to fail to start. | [systemd unit documentation](https://www.freedesktop.org/software/systemd/man/systemd.unit.html) |
| **VMware Tools kernel module conflicts** — If both `open-vm-tools` and proprietary VMware Tools kernel modules (`vmxnet`, `pvscsi`, `vmhgfs`) are loaded, they conflict and can prevent a clean conversion. | [VMware KB: open-vm-tools vs. VMware Tools](https://kb.vmware.com/s/article/2073803) |
| **Root filesystem free space** — virt-v2v checks for at least 100 MB free on each modified filesystem. The playbook enforces 1 GB as a conservative safety margin. | [virt-v2v man page — Free space for conversion](https://www.libguestfs.org/virt-v2v.1.html) |
| **Hardcoded MAC addresses in network config** — `HWADDR=` in RHEL `ifcfg` files or `hwaddress` in Debian `/etc/network/interfaces` bind the config to the old NIC. The MAC changes after migration. | [Red Hat KCS: Network interface does not come up after V2V](https://access.redhat.com/solutions/43526) |
| **Netplan configuration** — An invalid Netplan config on Ubuntu causes `netplan apply` to fail on first boot, leaving the VM without network. | [Netplan documentation](https://netplan.readthedocs.io/) |
| **Huge pages** — Huge page reservations are NUMA topology-dependent. If the KVM host NUMA topology differs from the VMware host, the reservation may fail at boot and starve applications. | [Red Hat KCS: Huge pages and V2V migration](https://access.redhat.com/solutions/3401051) |
| **AppArmor profiles referencing /dev/sd*** — AppArmor profiles that allow `/dev/sda` but not `/dev/vda` will silently deny access to the virtio block device after migration. | [AppArmor documentation](https://gitlab.com/apparmor/apparmor/-/wikis/home) |
| **auditd rules referencing /dev/sd*** — Audit rules like `-w /dev/sda` will fail silently or flood logs when the device is renamed to `/dev/vda` after migration. | [auditd man page](https://linux.die.net/man/8/auditd) |
| **Real-time kernel** — RT kernels (`+rt` / `-rt`) have stricter driver compatibility requirements. virtio drivers may cause latency spikes or fail to load with `CONFIG_PREEMPT_RT` builds. | [Red Hat KCS: Real-time kernel and KVM virtualization](https://access.redhat.com/solutions/2007221) |
| **Third-party backup agents** — Veeam, Commvault, and NetBackup use vSphere snapshot APIs for quiescing. These agents become non-functional after migration and may hold file locks during conversion. | [Veeam KB: VMware agent and V2V migration](https://www.veeam.com/kb3290); [Commvault documentation](https://documentation.commvault.com) |
| **SR-IOV / PCI passthrough** — VMs using SR-IOV or PCI passthrough are tied to specific physical hardware and cannot be live-migrated on KubeVirt without the appropriate device plugin. | [OpenShift Virtualization — SR-IOV documentation](https://docs.redhat.com/en/documentation/openshift_container_platform/latest/html/virtualization/virtual-machines#virt-configuring-sriov-device-for-vms) |
| **Static IP configuration** — Static IPs require explicit NIC-to-network mapping in the KubeVirt VM spec; without it the interface goes offline post-migration. | [Red Hat MTV docs — Network mapping](https://docs.redhat.com/en/documentation/migration_toolkit_for_virtualization/2.11/html/migrating_your_virtual_machines_to_red_hat_openshift_virtualization/) |
| **Multiple NICs** — VMs with 2+ NICs require explicit NIC-to-network mapping in the KubeVirt VM spec for each interface. | [Red Hat MTV docs — Network mapping](https://docs.redhat.com/en/documentation/migration_toolkit_for_virtualization/2.11/html/migrating_your_virtual_machines_to_red_hat_openshift_virtualization/) |
| **Non-standard MTU** — Custom MTUs (e.g. 9000 for jumbo frames) can cause packet fragmentation on OVN-Kubernetes overlay networks, which default to MTU 1400. | [OVN-Kubernetes MTU documentation](https://docs.openshift.com/container-platform/latest/networking/changing-cluster-network-mtu.html) |

### LOW — Informational or advisory checks

| Check | Reference |
|-------|-----------|
| **Cron jobs referencing external resources** — Cron jobs referencing NFS mounts, specific hostnames, or hardware devices may fail silently post-migration if those resources are unavailable. | General best practice |
| **Docker host device mounts** — Containers with `/dev/*` bind mounts reference devices that may not exist or be named differently on KVM. | [Docker documentation — Devices](https://docs.docker.com/reference/cli/docker/container/run/#device) |
| **Partition table type (MBR vs GPT)** — MBR is limited to 2 TB disks and may cause issues with large disks during conversion. GPT is preferred. | [virt-v2v man page — Disk conversion](https://www.libguestfs.org/virt-v2v.1.html) |
| **Disk SMART health status** — Pre-migration disk health check to avoid migrating a disk that is already failing. | [smartmontools documentation](https://www.smartmontools.org/) |
| **Swap uses UUID in fstab** — Swap entries using `/dev/sd*` paths in fstab will fail to activate after disk device rename. | [Red Hat KCS: fstab entries after V2V migration](https://access.redhat.com/solutions/1339763) |
| **Docker storage driver** — Docker using the `devicemapper` storage driver on top of LVM creates a complex block topology that does not translate cleanly to virtio block devices. | [Docker documentation — Storage drivers](https://docs.docker.com/engine/storage/drivers/) |
| **/tmp mount options** — `noexec` or `nosuid` on `/tmp` can prevent virt-v2v from executing helper scripts it writes during the customization phase. | [virt-v2v man page — Converting a Linux guest](https://www.libguestfs.org/virt-v2v.1.html) |
| **Syslog forwarding** — Log forwarding to a specific host may fail after migration if the target is on a different network segment. | General network best practice |
| **Timezone is UTC** — Mismatched timezones between source and target can cause log correlation issues and certificate validation failures. | [Red Hat KCS: Timezone configuration](https://access.redhat.com/solutions/5005521) |
| **Filesystem resize capability** — `ext2` / `ext3` filesystems do not support online resize; if virt-v2v needs to expand the filesystem it will fail. `ext4` and `xfs` support online resize. | [virt-v2v man page — Disk conversion](https://www.libguestfs.org/virt-v2v.1.html) |
| **GRUB video configuration** — `GRUB_GFXMODE` / `GRUB_GFXPAYLOAD` reference display hardware that does not exist on KVM, potentially causing boot delays or framebuffer errors. | [GNU GRUB manual — Simple configuration](https://www.gnu.org/software/grub/manual/grub/grub.html#Simple-configuration) |
| **resolv.conf management** — A static `/etc/resolv.conf` (not managed by NetworkManager, dhclient, or systemd-resolved) will not update when the VM's network is reconfigured post-migration. | [Red Hat KCS: resolv.conf and NetworkManager](https://access.redhat.com/solutions/7037862) |
| **Podman / Docker containers running** — Live containers should be stopped before migration for filesystem consistency; running containers hold open file handles that could cause inconsistency in the migrated image. | [Red Hat MTV docs — Migration prerequisites](https://docs.redhat.com/en/documentation/migration_toolkit_for_virtualization/2.11/html/migrating_your_virtual_machines_to_red_hat_openshift_virtualization/) |
| **virt-who VMware configuration** — RHEL subscriptions registered with virt-who in VMware mode are tied to the hypervisor UUID. After migration the UUID changes and the subscription will de-register within the grace period. | [Red Hat KCS: virt-who after hypervisor migration](https://access.redhat.com/solutions/1207133) |
| **journald persistent storage** — Large persistent journal files inflate the converted disk image unnecessarily. | [systemd-journald documentation](https://www.freedesktop.org/software/systemd/man/journald.conf.html) |
| **cloud-init VMwareGuestInfo datasource** — OpenShift Virtualization injects VM configuration via the `VMwareGuestInfo` datasource. Without it, cloud-init will not configure networking on first boot. | [cloud-init VMwareGuestInfo datasource docs](https://cloudinit.readthedocs.io/en/latest/reference/datasources/vmware.html) |

## post-migration-linux.yml

| Check | Reference |
|-------|-----------|
| **Platform is KVM (not VMware)** — The primary post-migration gate: confirms the VM is running on KVM and not still on VMware. | [virt-v2v man page — Verifying conversion](https://www.libguestfs.org/virt-v2v.1.html) |
| **VMware kernel modules unloaded** — Any VMware module (`vmxnet3`, `pvscsi`, `vmmemctl`, `vmci`) still loaded indicates an incomplete or failed conversion. | [virt-v2v man page — Converting a Linux guest](https://www.libguestfs.org/virt-v2v.1.html) |
| **virtio_blk / virtio_scsi driver loaded** — The VM must use virtio block drivers to access its disk on KVM. | [virt-v2v man page — Converting a Linux guest](https://www.libguestfs.org/virt-v2v.1.html) |
| **virtio_net driver loaded** — The VM must use the virtio network driver for proper KVM networking. | [virt-v2v man page — Converting a Linux guest](https://www.libguestfs.org/virt-v2v.1.html) |
| **Root disk is virtio (vda)** — After conversion the primary disk should be presented as `/dev/vda` (virtio-blk) or via virtio-scsi. | [virt-v2v man page — Converting a Linux guest](https://www.libguestfs.org/virt-v2v.1.html) |
| **Primary NIC uses virtio_net** — All non-loopback interfaces should be driven by `virtio_net` post-migration. | [virt-v2v man page — Converting a Linux guest](https://www.libguestfs.org/virt-v2v.1.html) |
| **open-vm-tools package removed** — The VMware guest agent must not be present on a KVM guest. virt-v2v removes it automatically; its presence indicates a failed conversion. | [virt-v2v man page — Converting a Linux guest](https://www.libguestfs.org/virt-v2v.1.html) |
| **vmtoolsd service not running** — The VMware tools daemon must not be active post-migration. | [VMware KB: VMware Tools removal](https://kb.vmware.com/s/article/1014522) |
| **fstab has no stale /dev/sd* references** — After conversion disks are `/dev/vd*`; stale `/dev/sd*` entries in fstab will prevent boot. | [Red Hat KCS: fstab entries after V2V migration](https://access.redhat.com/solutions/1339763) |
| **qemu-guest-agent installed and running** — OpenShift Virtualization uses qemu-guest-agent for IP address reporting, snapshot freeze/thaw, and live migration coordination. | [MTV docs — Understanding MTV migration](https://docs.redhat.com/en/documentation/migration_toolkit_for_virtualization/2.11/html/migrating_your_virtual_machines_to_red_hat_openshift_virtualization/assembly_understanding-mtv-migration_mtv); [OpenShift Virtualization — qemu-guest-agent](https://docs.redhat.com/en/documentation/openshift_container_platform/latest/html/virtualization/virtual-machines#virt-installing-qemu-guest-agent) |
| **EDR interference with qemu-guest-agent** — EDR tamper-protection rules can prevent qemu-guest-agent from starting. | [CrowdStrike KB: Allow-listing processes](https://supportportal.crowdstrike.com); [SentinelOne exclusion documentation](https://docs.sentinelone.com) |
| **VMware Tools files absent** — Leftover `/usr/bin/vmware-toolsd`, `/etc/vmware-tools`, or `/usr/lib/vmware-tools` indicate an incomplete conversion cleanup. | [virt-v2v man page — Converting a Linux guest](https://www.libguestfs.org/virt-v2v.1.html) |
| **No VMware packages remaining** — Any package matching `vmware` or `open-vm-tools` still installed indicates incomplete conversion cleanup. | [virt-v2v man page — Converting a Linux guest](https://www.libguestfs.org/virt-v2v.1.html) |
| **VMware udev rules removed** — udev rules referencing `vmware`, `vmxnet`, or `pvscsi` must be removed post-migration to avoid device naming conflicts. | [Red Hat KCS: 70-persistent-net.rules after V2V](https://access.redhat.com/solutions/49705) |
| **Persistent net rules absent** — `/etc/udev/rules.d/70-persistent-net.rules` must be removed; the old MAC-to-interface binding is invalid after migration. | [Red Hat KCS: 70-persistent-net.rules after V2V](https://access.redhat.com/solutions/49705) |
| **FQDN resolves** — Confirms DNS is functional and the VM's hostname is resolvable after network reconfiguration. | General networking best practice |
| **NTP / chrony running** — Clock sync is critical post-migration; a drifted clock breaks TLS and Kerberos authentication. | [Red Hat KCS: Clock sync after migration](https://access.redhat.com/solutions/17248) |
| **cloud-init completed successfully** — cloud-init handles first-boot network config, hostname, and SSH keys on KubeVirt; a failed run means the VM may be misconfigured. | [cloud-init documentation — Status](https://cloudinit.readthedocs.io/en/latest/reference/cli.html#status) |
| **SELinux autorelabel file consumed** — virt-v2v relabels SELinux contexts during conversion. If it falls back to the `/.autorelabel` method, the file is consumed on first boot. If `/.autorelabel` still exists after first boot, SELinux relabeling did not complete. | [virt-v2v man page — `--no-selinux-relabel`](https://www.libguestfs.org/virt-v2v.1.html) |
| **Hostname matches inventory** — Post-migration hostname drift can indicate that cloud-init or the VM's hostname configuration was not correctly applied. | General best practice |
| **SSH host keys present** — virt-v2v preserves SSH host keys; if absent, clients will receive host key warnings on the first connection. | [virt-v2v man page — Converting a Linux guest](https://www.libguestfs.org/virt-v2v.1.html) |
| **Root filesystem free space post-migration** — Ensures the conversion process did not fill the root filesystem. | [virt-v2v man page — Free space for conversion](https://www.libguestfs.org/virt-v2v.1.html) |
